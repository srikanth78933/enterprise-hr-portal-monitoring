# Enterprise HR Portal – Monitoring (ELK)

Logs and metrics for the **prod** EKS cluster, collected by Filebeat and Metricbeat and stored in an
ELK stack (Elasticsearch, Logstash, Kibana) that runs on one EC2 instance outside the cluster.

```
┌─ prod EKS cluster ─────────────────────────┐        ┌─ ELK EC2 (private subnet) ─────────────────┐
│  Filebeat   (DaemonSet, every node) ───────┼─5044──►│  Logstash  parses Spring Boot logs          │
│     container logs + pod labels            │        │     │                                       │
│                                            │        │     ▼                                       │
│  Metricbeat (DaemonSet, every node) ───────┼─9200──►│  Elasticsearch  data on its own EBS volume  │
│     node, pod and container metrics        │        │     ▲                                       │
└────────────────────────────────────────────┘        │  Kibana :5601 ◄── ALB (your IPs only) ◄── you
                                                      └─────────────────────────────────────────────┘
```

- Logs appear in Kibana about **2–5 seconds** after a pod writes them.
- The ELK instance, its security groups, data volume, passwords and Kibana load balancer are created by
  [enterprise-hr-portal-infra](https://github.com/srikanth78933/enterprise-hr-portal-infra) (`enable_elk = true` in prod).
- This repo holds what runs on the instance and in the cluster, plus the Jenkins pipeline that deploys both.

## Repository layout

```
enterprise-hr-portal-monitoring/
├── Jenkinsfile                    Deploys ELK to the EC2 instance (S3 + SSM) and the Beats to EKS (Helm)
├── elk/                           Copied to /opt/elk on the ELK instance
│   ├── docker-compose.yml         Elasticsearch, Logstash, Kibana
│   ├── elk.env                    Version, heap sizes, retention days (no secrets)
│   ├── logstash/config/logstash.yml
│   ├── logstash/pipeline/logstash.conf   Spring Boot log parsing, routing to data streams
│   └── scripts/
│       ├── deploy.sh              Reads passwords from Secrets Manager, writes .env, starts the stack
│       └── setup.sh               Users/roles, retention, Metricbeat dashboards, Kibana data views
├── helm/beats/                    Filebeat + Metricbeat DaemonSets, RBAC, config
└── environments/prod/values.yaml  Prod overrides for the Beats chart
```

## What ends up in Elasticsearch

| Data stream / index                    | Content | Kept |
|----------------------------------------|---------|------|
| `logs-hr_portal-prod`                  | HR Portal logs, parsed: `log.level`, `log.logger`, `process.thread.name`, `service.name`, message with stack trace | 14 days |
| `logs-kubernetes.container_logs-prod`  | All other containers (ingress controller, add-ons, …) | 14 days |
| `metricbeat-*`                         | Node CPU/memory/disk/network, pod and container CPU/memory | 7 days |

Every log event also carries `kubernetes.namespace`, `kubernetes.pod.name`, `kubernetes.node.name`
and the pod labels, so you can filter by any of them. Java stack traces are joined to the log line
they belong to (one event, not one per line).

Retention is set in `elk/elk.env` (`LOGS_RETENTION_DAYS`, `METRICS_RETENTION_DAYS`) and applied by
Elasticsearch ILM.

## Security

- The ELK instance has no public IP and no SSH; it is managed through **AWS Systems Manager**.
- Security groups: Logstash (5044) and Elasticsearch (9200) accept only the EKS nodes;
  Kibana (5601) accepts only its load balancer, which accepts only `kibana_allowed_cidrs`.
- Passwords are generated by Terraform and stored in Secrets Manager (`enterprise-hr-portal/prod/elk`).
  Nothing secret is in this repo.
- Shippers use least-privilege users: `logstash_writer` (write `logs-*`) and `metricbeat_writer`
  (write `metricbeat-*`). Only setup and people use the `elastic` superuser.

## Prerequisites

1. The prod infrastructure exists, with `enable_elk = true` (infra repo, `environments/prod`).
2. On the Jenkins server: AWS CLI v2, `kubectl`, `helm`, `jq` (the deploy repo README covers the first three;
   `sudo apt install -y jq`).
3. The Jenkins IAM user may use: `ec2:DescribeInstances`, `s3` on the config bucket, `ssm:SendCommand`,
   `ssm:GetCommandInvocation`, `secretsmanager:GetSecretValue` on `enterprise-hr-portal/prod/elk`,
   `elasticloadbalancing:DescribeLoadBalancers`, and EKS access (already granted through `cluster_admin_arns`).

## Create the Jenkins job

1. **New Item** → `enterprise-hr-portal-monitoring` → **Pipeline**.
2. **Pipeline script from SCM** → Git → `https://github.com/srikanth78933/enterprise-hr-portal-monitoring.git`,
   branch `*/main`, script path `Jenkinsfile` → **Save** → **Build Now**.
3. Approve the deploy when the pipeline pauses.

| Stage               | What it does |
|---------------------|--------------|
| Validate            | Syntax-checks the scripts, lints the Beats chart |
| Find ELK Instance   | Looks up the instance by its `Name` tag; gets its private IP and the config bucket |
| Approve             | Manual approval (production) |
| Upload ELK Config   | `aws s3 sync elk/` to the config bucket |
| Deploy ELK on EC2   | SSM runs `scripts/deploy.sh` on the instance and shows its output |
| Beats Credentials   | Creates the `elk-credentials` Kubernetes Secret from Secrets Manager |
| Deploy Beats to EKS | `helm upgrade --install beats` with `elk.host` = the instance's private IP |

The first run takes about 10 minutes (image downloads and Kibana dashboard import). Later runs are faster.
Running the pipeline again is safe: every step updates in place.

## Open Kibana

The pipeline prints the URL at the end. You can also get it from Terraform:

```bash
cd enterprise-hr-portal-infra/environments/prod
terraform output elk          # kibana_url, private_ip, instance_id
```

Log in as `elastic`. The password:

```bash
aws secretsmanager get-secret-value --secret-id enterprise-hr-portal/prod/elk \
  --query SecretString --output text | jq -r .elastic_password
```

Where to look:

| Goal | In Kibana |
|------|-----------|
| HR Portal logs, live | **Discover** → data view *HR Portal application logs* → turn on auto-refresh (5 s) |
| Only errors | Discover, query `log.level : "ERROR"` |
| One pod or namespace | Discover, query `kubernetes.pod.name : "enterprise-hr-portal-*"` |
| Node and pod metrics | **Dashboards** → `[Metricbeat Kubernetes] Overview`, `[Metricbeat System] Host overview` |
| Alerts | **Stack Management → Rules** → e.g. *Elasticsearch query*: `log.level:ERROR` more than 10 in 5 minutes |

## Operating the ELK instance

Connect without SSH:

```bash
aws ssm start-session --target <instance_id>
sudo -i
cd /opt/elk
docker compose ps                     # container status
docker compose logs -f logstash       # follow Logstash logs
df -h /data                           # Elasticsearch disk usage
```

Useful Elasticsearch checks (on the instance):

```bash
source /opt/elk/.env
curl -s -u elastic:$ELASTIC_PASSWORD localhost:9200/_cluster/health?pretty
curl -s -u elastic:$ELASTIC_PASSWORD "localhost:9200/_cat/indices/.ds-*?v&s=index"
```

- **Upgrade the stack:** change `ELASTIC_VERSION` in `elk/elk.env` and `version` in `helm/beats/values.yaml`,
  then run the pipeline.
- **Disk space:** lower the retention days, or increase `elk_data_volume_size` in the infra repo and grow the
  file system with `xfs_growfs /data`.
- **Backups:** take EBS snapshots of the data volume (for example with AWS Backup).

## Local test (optional)

The stack runs on any Linux machine with Docker, without AWS:

```bash
cd elk
export ELASTIC_PASSWORD=... KIBANA_SYSTEM_PASSWORD=... LOGSTASH_WRITER_PASSWORD=...
export METRICBEAT_WRITER_PASSWORD=... KIBANA_ENCRYPTION_KEY=<32 characters>
sed -i 's#^DATA_DIR=.*#DATA_DIR=/tmp/elk-data#; s#^ES_HEAP=.*#ES_HEAP=1g#' elk.env
sudo -E ./scripts/deploy.sh          # then open http://localhost:5601
```
